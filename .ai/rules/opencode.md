# Opencode

## opencode-mcp tools: text-only responses and the abort 'id' gotcha
opencode-mcp (v1.11.0) tools always return structuredContent=null — extract everything by parsing the text (session ids via regex ses_[A-Za-z0-9]+). OpencodeSessionManager centralizes the whitelist (project dirs must be strictly inside OpencodeSetting::singleton()->root_projects_path) and always passes the absolute `directory` explicitly. Gotcha: opencode_session_abort expects the session under `id`, not `sessionId` (all other session tools use `sessionId`). Do NOT use opencode_wait/run in the monitor — use opencode_fire/check/conversation; checkSession treats `Status: **idle**`/`**completed**`/`Done!` as finished. Client::disconnect() kills opencode-mcp cleanly but the auto-started `opencode serve` daemon persists and is reusable.

## OpencodeSessionManager must not be modified to expose opencode_command_execute
opencode-mcp v1.11.0 DOES expose a slash-command tool (opencode_command_execute, needs sessionId + command) and every workflow step (context-gather, plan, plan-feature/bugfix/refactor, execute, validate, skill-review, commit) is a registered slash command, but OpencodeSessionManager exposes no command-execution method and must not be modified. Steps are dispatched by the tools via fire/reply prompts instead.

## OpencodeMonitor: no Completed on failed send; failures are retried or failed after MAX_FAILURES
opencode:monitor (Running workflows only) checks each session via checkSession/conversation (never wait/run). When finished it completes the current step, sends the owner a Telegram message via OpencodeNotifier::notify(int $chatId, string $markdown): bool (formatting via TelegramHtmlFormatter, lazy TelegramClient), and transitions: questions → WaitingConfirmation/Answer; next step → WaitingConfirmation/Proceed; last step → Completed only if notify() returned true. On a failed final send the workflow STAYS Running with failure_count incremented so the next tick re-detects the finished session and retries — never WaitingConfirmation (the monitor only polls status=running, so that would freeze it). completeCurrentStep only completes the Running step matching current_step (falls back to the most recent Running step) and never touches Completed/Failed steps. A successful tick (notify returned true) resets failure_count to 0. MAX_FAILURES (3) consecutive failures → Failed + DecisionOnFailure with /retry or /abort, where a "failure" is a check OpencodeException, a null opencode_session_id, or a failed final notify. last_summary always stores the sent message. OpencodeSessionManager is a singleton (AppServiceProvider) — disconnect() in a finally so the shared client is closed per scheduled tick.

## OpencodeSessionWatcher: single check() entry, no-throw, retry-on-failed-notify
OpencodeSessionWatcher::check() is the single public entry for external-session discovery; invoked periodically from opencode:monitor and must never throw. Sessions are discovered from the opencode SQLite via OpencodeSessionStore (activeSessions/sessionState/hasTerminalError — see "External-session discovery reads opencode's SQLite via OpencodeSessionStore"), while MCP calls are wrapped in try/catch(OpencodeException) (conversation/pendingPermissions) and isAllowedProject in try/catch(Throwable). Owner chat = resolveOwnerChatId() (see "OpencodeSessionWatcher owner chat prefers allowed_user_ids"); no owner/chat → Log::debug + return. Sessions with an OpencodeWorkflow.opencode_session_id are excluded; pendingPermissions sessionIds add to question detection. A freshly discovered watch (wasRecentlyCreated) is register-only EXCEPT a live 'question' turn, which is inspected and notified in the same discovery tick via inspectFreshSession (see "Watcher notifies a live question turn on the first discovery tick"); every other first-tick outcome stays register-only. On notify() returning false the watch's last_seen_status is NOT updated so the next tick retries.

## OpencodeSessionWatcher owner chat prefers allowed_user_ids
OpencodeSessionWatcher::resolveOwnerChatId() resolves the owner's Telegram chat by preferring the most recent TelegramChatConversation whose chat_id is inside TelegramSetting::singleton()->allowed_user_ids (int-cast array). When allowed_user_ids is empty/null or no owner conversation matches it, it falls back to the latest owner conversation (latest('id')). This prevents a stale/dead conversation (e.g. chat 123456789 from tests, 'chat not found' on send) from being chosen over the real allowed chat. Both queries order by latest('id').

## OpencodeSessionWatcher never-throws contract
OpencodeSessionWatcher::check() must never let an exception escape, or a single failing session would abort the whole opencode:monitor tick (and the workflow loop). Every OpencodeSessionStore call is wrapped in try/catch(Throwable) and every OpencodeSessionManager call (conversation, pendingPermissions) in try/catch(OpencodeException) (transport failures are wrapped into OpencodeException by callTool). Persisted status is canonical: 'completed' is normalized to 'idle'.

## OpencodeSessionWatcher smoke tests against the real DB actually send Telegram notifications
Running opencode:monitor or OpencodeSessionWatcher::check() against the real local opencode.db with a configured bot token WILL notify the owner's real chat: fresh (within RECENT_ACTIVITY_HOURS=24h) failing sessions trigger notifyError, and genuine working->stopped sessions trigger finished only after staying idle for the FINISH_CONFIRM_MINUTES (3) confirmation window — a short smoke run may not observe a finish. A smoke run against real data is not side-effect-free. The full first tick is also slow (the Task F live run over ~11k sessions exceeded 180s and had to finish in the background — fsync-bound inserts + per-session PDO/realpath/MCP pending-permissions call); the opencode serve daemon spawned by the manager persists and spins CPU. Use a stubbed store + notifier in tests.

## Terminal error signal: only notify when the most recent part is a real tool error
The raw has_error_part flag (any tool part in error state) is ~100% false positive — opencode error parts are normal iterative debugging (rule-blocked, aborted, edit oldString not found), so it notified 97 fake failures. Use OpencodeSessionStore::hasTerminalError(): true only if the LAST part (ORDER BY time_created DESC LIMIT 1) is a tool part with state.status=error AND state.error does not match NON_TERMINAL_ERROR_MARKERS ('tool execution aborted', 'task cancelled', 'dismissed this question', 'prevents you from using'). The error text lives in part.data -> state.error (verified: present in 100% of error parts, state.output never used). The watcher additionally requires !has_running_part and a 24h per-session cooldown on notified_at before re-notifying. Verified against the real DB: 87 fresh error sessions -> 0 terminal.

## OpencodeSessionWatcher guards every OpencodeSessionStore call
OpencodeSessionWatcher::check() never-throws contract requires every OpencodeSessionStore call to be wrapped in try/catch(Throwable): activeSessions() (in check), sessionState() and hasTerminalError() (in inspectSession, each returns without touching the watch row so the previous status is preserved). The hasTerminalError guard was missing after the store rewrite (Tarea C) and was added with the Tarea D tests — keep it if the error path is ever touched again.

## External-session discovery reads opencode's SQLite via OpencodeSessionStore
OpencodeSessionWatcher discovers external sessions via OpencodeSessionStore::activeSessions() (read-only PDO over the opencode.db SQLite: mode=ro + PRAGMA query_only), classifies via sessionState(), and detects failure via hasTerminalError(). The MCP client (OpencodeSessionManager) is only used for conversation(), pendingPermissions(), and the isAllowedProject() whitelist check. listSessions()/sessionInfo()/sessionProgress() were removed as dead code (Tarea E) — never re-add discovery from MCP text output.

## Watcher finish requires a confirmation window — working→stopped does not notify immediately
OpencodeSessionWatcher does NOT notify "terminó" on the live working->stopped transition; a stop is only reported once the session has stayed idle for the confirmation window. Mechanism: the first observation of has_running_part === false (with parts) promotes the watch to a 'stopping' candidate with NO notification; while 'stopping' the session is re-inspected every tick (STABLE_RECHECK_MINUTES applies only to confirmed 'stopped' watches); and the finish (notifyFinished) fires ONLY when last_seen_status is 'working' or 'stopping' AND the session's effective last-activity (the discovery row's time_updated = MAX(session.time_updated, MAX(part.time_created)), via updatedAtFromEpochMs) is at least FINISH_CONFIRM_MINUTES (3) minutes old. A resume (has_running_part true) resets the watch to 'working' in the working branch and silently discards the candidate — the session is never notified as finished. Rationale: opencode writes "thinking gaps" (step-finish → step-start → reasoning parts, none with state.status='running') of 16-83s+ between tool calls, and a watcher tick (~1 min) could land inside a gap and fire a false "terminó" on a live session (hard evidence: 3 real sessions produced 37, 5, and 39 parts AFTER the notification; one kept delegating subagents). A genuine finish is indistinguishable from a transient gap in the DB — the only reliable discriminator is idle time. There is no bootstrap/neverNotified+isFresh notify branch — an already-stopped session discovered on the first tick (watch born 'unknown') is registered but never notified. The set of sessions the watcher inspects is scoped by the session_watch_since watermark (see "Watcher discovery uses session_watch_since watermark, not startOfDay"), NOT by a day cutoff — activeSessions() no longer filters by startOfDay. RECENT_ACTIVITY_HOURS (24h) is still used solely to gate the error signal (hasTerminalError && !running && (fresh || was working)). A fresh watch is born 'unknown', so the only first-tick notification is a live 'question' turn (inspectFreshSession — see "Watcher notifies a live question turn on the first discovery tick"); never generalize it into a bootstrap notify or the mass-notification spam (310 messages) returns.

## Sub-agent sessions are tracked but never notified (parent_id signal)
OpencodeSessionStore::activeSessions() returns parent_id per session (100% reliable sub-agent marker: sub-agents have parent_id set, TUI sessions NULL). OpencodeSessionWatcher sets watch.is_subagent from parent_id at firstOrCreate and keeps it true on every update; sub-agent sessions short-circuit in trackSubagent() (status working/stopped + checked_at only) BEFORE the terminal-error/finished paths, so they never call notifyError/notifyFinished/notify. TUI sessions (parent_id null) keep the normal notify flow. Do not remove the sub-agent guard — it prevents sub-agent spam.

## Session-watch watermark: start-of-boot cutoff, fixed between restarts
OpencodeSessionStore::activeSessions(?int $sinceEpochMs = null) no longer filters by startOfDay — it returns every non-archived session, optionally >= the given watermark, applied to EFFECTIVE freshness (max of session.time_updated and the most recent part's time_created — see "activeSessions discovery uses part freshness"), so an actively-asking session whose question part was written after the cutoff stays discoverable even though session.time_updated went stale. OpencodeSessionWatcher resolves the watermark from opencode_settings.session_watch_since: null or >10 min old (monitor's withoutOverlapping window) means a restart, so it resets to now() and passes it to activeSessions(). This is now the FALLBACK path — when opencode_settings.schedule_booted_at (the boot anchor, see "Watcher boot anchor") is set and newer, resolveWatchSince re-arms with the anchor instead, so restarts inside the 10-min window are still detected. The watermark is NOT advanced per tick — an idle session waiting for input keeps a stale time_updated and must stay discoverable. If reading/writing settings throws, degrade to activeSessions() with no cutoff (never break the tick).

## OpencodeSessionWatcher skips dismissed sessions before inspect
check() loads dismissed session ids from opencode_session_dismissals (private dismissedSessionIds(), try/catch → [] so the never-throws contract holds) and skips those sessions before inspectSession — they are never registered, inspected or notified. Keep the skip next to the workflow-session exclusion and keep the debug log line.

## Watcher discovery uses session_watch_since watermark, not startOfDay
OpencodeSessionStore::activeSessions(?int $sinceEpochMs) no longer filters by startOfDay. OpencodeSessionWatcher resolves session_watch_since from opencode_settings: resets it to now() when null or when now() - since > WATCH_WATERMARK_RESTART_MINUTES (10), then passes it as epoch ms cutoff. The cutoff applies to EFFECTIVE freshness (max of session.time_updated and MAX(part.time_created)): opencode does not bump session.time_updated when it writes a question part, so part freshness is what keeps an actively-asking session discoverable below the cutoff. The watermark stays fixed until the next detected restart (it must NOT advance each tick, or idle sessions waiting for user input would drop out of discovery and never notify). Supersedes the earlier "store filters by current day" guidance.

## has_running_part es poco fiable: opencode deja parts tool 'running' stale
En opencode.db, solo los parts tipo tool llevan data.state.status, y los tools 'question'/'task' quedan en 'running' mientras esperan. Pero opencode DEJA parts 'running' stale permanentemente (question respondidas sin flipar, tasks abortados con time.end=NULL), así que EXISTS(...status='running') marca sesiones terminadas como working para siempre (zombies reales en ses_02c64518 y ses_030afc29). Para clasificar sesiones: un part running es VIVO solo si time_created > MAX(step-finish de la sesión); si el running más reciente es un tool 'question', la sesión espera input del usuario (no working ni stopped). step-finish es el único marcador de cierre de turno.

## Watcher boot summary: one consolidated message per detected restart
OpencodeSessionWatcher sends a SINGLE aggregate Telegram message ("Sesiones activas desde el inicio del servidor:") listing up to MAX_BOOT_SUMMARY_SESSIONS (10) live sessions discovered within the reset watermark on the first tick after a restart. Gated by opencode_settings.session_watch_boot_reported_at (armed to null in resolveWatchSince when a restart is detected, persisted only after a successful notify). When no relevant session exists the boot STILL sends an immediate empty-boot message ("Sistema DevWarden iniciado. No hay sesiones de opencode activas.") so the owner always gets a notification per restart. This is an intentional, user-approved one-message summary — NOT the old per-session bootstrap notify that caused 310-message spam. Never "fix" it back into per-session notifications.

## Watcher boot anchor: schedule_booted_at (CommandStarting listener for schedule:work) is the authoritative restart signal
The boot summary re-arms on EVERY real schedule:work start, not only on the 10-min watermark heuristic. registerScheduleWorkBootListener() in app/Providers/AppServiceProvider.php listens for Illuminate\Console\Events\CommandStarting and, ONLY when $event->command === 'schedule:work', stamps opencode_settings.schedule_booted_at = now() and re-arms session_watch_boot_reported_at = null (best-effort try/catch(Throwable) → Log::debug; never throws). OpencodeSessionWatcher::resolveWatchSince() then treats schedule_booted_at as the authoritative restart signal: if it is set and newer than session_watch_since (or that is null) → session_watch_since = schedule_booted_at + re-arm the boot marker. The >10-min watermark heuristic remains ONLY as a FALLBACK for installs where schedule_booted_at is null — never let it run when the anchor is present. Fallback race trap: once the anchor is set and already adopted (session_watch_since == schedule_booted_at), the anchor branch is a no-op (isAfter on equality is false) and the code MUST NOT drop into the >10-min elseif — doing so re-arms the boot marker and re-sends the boot summary ~10 minutes after the real boot (bug real reportado: dev:full corriendo ~10 min reenvió "Sesiones activas desde el inicio del servidor"). This fixes the "boot summary not sent (or ~7 min stale) on rapid dev:full restarts < 10 min" bug — do not reintroduce the watermark-reset as the only boot detection, and do not let the fallback fire when the anchor already exists.

## Watcher question-turn milestone: one notify per live 'question' turn
A session with a LIVE running part whose last_turn_tool === 'question' (waiting for user input) triggers notifyQuestionTurn once per turn. Anti-spam = last_notified_event === 'question' on the watch; the marker is reset to null as soon as the session works on a non-question tool, so the NEXT question turn notifies again. A question that stays pending for hours is never re-notified (no time window). Tradeoff: two quick successive questions between ticks can under-report (acceptable, favors anti-spam).

## Watcher finish classification is DB-first — notifyFinished never re-classifies by text
notifyFinished() reports event 'question' ONLY when the session id is in the pending-permission list; the parser->hasQuestions($last) heuristic was REMOVED from the classification (the $last assistant text is still used to build the summary). A genuinely waiting session is handled earlier by the question-turn branch on the authoritative DB signal (last_turn_tool === 'question' with a live running part) — by the time notifyFinished runs the session is stopped (no live running part), so the text heuristic was a false-positive factory: a session whose final assistant text ended with a rhetorical question ('¿Procedemos con algo concreto...?') was emitted as 'question' with the already-answered options and permanently swallowed the real finish (watch stuck at last_seen_status='stopped' + last_notified_event='question'). A rhetorical trailing question must NEVER suppress the "La sesión ... terminó." message.

## Watcher boot summary: grace window + immediate empty-boot message
The boot summary never seals session_watch_boot_reported_at silently. On a detected restart, resolveWatchSince resets the watermark to now() and that fresh value used as the discovery cutoff would miss sessions updated a few seconds earlier (boot race). Fix: maybeSendBootSummary re-runs activeSessions() with cutoff = watermark - BOOT_SUMMARY_GRACE_MINUTES (5 min); if no relevant session exists it sends an immediate empty-boot message (formatBootSummaryEmpty) in the same tick and seals only after that notify() succeeds — a failed send is retried next tick exactly like the non-empty branch. BOOT_SUMMARY_RETRY_WINDOW_MINUTES and isWithinBootRetryWindow() were REMOVED (user decision: always notify at boot, no silent seal). Marking still happens only after a successful notify().

## Watcher question notifications are plain text (no inline keyboard, no oq:)
OpencodeSessionWatcher no longer attaches inline keyboards to question notifications: buildQuestionNotification() returns the plain-text message string (header + Sesión: ses_xxx + numbered 'Pregunta N:' + lettered '(a) label' options), and notifyQuestionTurn()/notifyFinished() call OpencodeNotifier::notify($chatId, $message) with the 2-arg signature. optionButtonText() and OPTION_BUTTON_MAX_LENGTH were removed; optionLetter() stays (used in the text). No 'oq:' callback_data is ever generated by the watcher anymore. The removed inline-button pipeline (callback_data contract oq:{session_id}:{question_index}:{option_index}, HandleTelegramCallbackQuery, answerCallbackQuery, reply_markup, inline_keyboard) is GONE by user decision — do not reintroduce it; questions are answered via OpencodeAskTool by the bot.

## OpencodeSessionStore::questionOptions() reads the 'question' field (fallback 'header'), not 'title'
questionOptions(string $sessionId) reads the MOST RECENT tool='question' part (ORDER BY time_created DESC, rowid DESC LIMIT 1, running or completed) and extracts state.input.questions[].options[] from its JSON, normalizing every option to {label, description} and dropping questions with no valid option. The question TEXT comes from $question['question'] with $question['header'] as fallback — NOT 'title' (verified: 0/1089 opencode part questions carry a 'title' key, all carry 'question'). Returns list<array{question: string, options: list<array{label, description}>>}; [] when there is no question part or anything unreadable; never throws (try/catch → [], Log::debug). Consumers: the watcher (plain-text 'Pregunta N:' lines in buildQuestionNotification) and BotAgent's <active_opencode_sessions> block (see .ai/rules/agents.md).

## Watcher discovery uses a grace window around the watermark
OpencodeSessionWatcher::discoveryCutoff() runs activeSessions($since - DISCOVERY_GRACE_MINUTES=5) for the main session loop, not the strict watermark. The watermark resets to now() on restart detection and would silently drop a session that went idle just before the reset (it goes idle with a stale time_updated, so it stays below the cutoff forever and its question-turn never notifies). Effective freshness (session.time_updated OR MAX(part.time_created)) only revives a session whose last part was written after the cutoff, so the grace window is still required for sessions whose last activity predates the reset. Keep the grace window; only old sessions (outside the 5-min window) are excluded.

## Boot summary excludes waiting sessions; question turn always fires
The boot summary lists ONLY working sessions; sessions with a live 'question' turn are excluded and always get their own question-turn notification (which carries the question text). There is NO boot-window dedup: do not suppress the question turn because the summary ran in the same tick, or the user loses the question content.

## Boot summary anclado a schedule_booted_at (listener de schedule:work)
El boot summary se re-arma en cada arranque real de schedule:work vía schedule_booted_at (columna en opencode_settings, estampada por el listener CommandStarting en AppServiceProvider, solo cuando $event->command === 'schedule:work'). El heurístico >10 min del watermark queda como fallback SOLO cuando schedule_booted_at es null. Cuando el anchor existe pero ya fue adoptado (session_watch_since == schedule_booted_at), NO re-armar nada — si el código cae al elseif del fallback (>10 min), reenvía el boot summary ~10 min después del arranque (bug real). Esto arregla el bug de resumen no enviado/desfasado en reinicios rápidos de dev:full.

## OpencodeSessionParser.lastAssistantText salta literales "(no content)" de opencode-mcp
opencode-mcp v1.11 renderiza el literal "(no content)" en el transcript cuando un mensaje assistant solo hizo tool calls (sin texto) — desalineación de tipos "tool" vs "tool-invocation"/"tool-result" (dist/helpers.js). El literal NO está en app/ ni tests/ (grep no lo encuentra; solo en el paquete). lastAssistantText() salta bloques assistant con text==='' O literal no-descriptivo (NON_DESCRIPTIVE_LITERALS = ['(no content)']) y hace fallback al último assistant con contenido real; si ninguno, devuelve trim($conversation) (intacto). "Agent performed N action(s)" NO se ignora (no es literal fijo, embebe contador N + tool summaries con contenido útil). Un solo fix en el parser cubre watcher (OpencodeSessionWatcher) y monitor (OpencodeMonitor), que comparten el parser.

## Boot summary vacío envía mensaje inmediato (sin retry window)
El boot summary SIEMPRE notifica al arrancar schedule:work; si no hay sesiones activas envía "Sistema DevWarden iniciado. No hay sesiones de opencode activas." en el primer tick (formatBootSummaryEmpty), sin ventana de retry. El marker session_watch_boot_reported_at se sella solo tras notify() exitoso y reintenta en fallo. NO reintroducir sellado silencioso para boots vacíos.

## Fallback watermark >10 min SOLO con anchor null (evitar reenvío del boot summary)
El fallback de restart por watermark >10 min en resolveWatchSince() aplica únicamente cuando schedule_booted_at es null. Cuando el anchor existe pero ya fue adoptado (session_watch_since == schedule_booted_at), NO re-armar el boot marker ni resetear el watermark — si el código cae al fallback, el boot summary se reenvía ~10 min después del arranque (bug real: dev:full corriendo ~10 min reenvió "Sesiones activas desde el inicio del servidor").

## resolveWatchSince: an adopted boot anchor must never re-arm, even past 10 min
The >10-min watermark fallback in resolveWatchSince() applies ONLY when schedule_booted_at is null. When the anchor exists and was already adopted (session_watch_since == schedule_booted_at, isAfter strict is false), return the watermark untouched — a service running >10 min is NOT a restart, so do not re-arm session_watch_boot_reported_at or reset session_watch_since to now(). The pre-fix code fell through to the elseif and re-sent the boot summary ~10 min after boot (schedule_booted_at 15:48 + resend at 15:58).

## activeSessions discovery uses part freshness — opencode does not bump session.time_updated on question parts
opencode leaves session.time_updated stale when it writes a question tool part (verified: part time_created 15:51:16.692 vs session.time_updated 15:51:13.741). activeSessions() therefore treats a session as fresh when EITHER session.time_updated >= cutoff OR its most recent part (MAX(part.time_created)) is >= cutoff, and returns the effective max as time_updated. Do not revert to filtering only by session.time_updated — it re-hides sessions actively asking questions below the watermark cutoff and delays the question notification by minutes.

## Watcher notifies a live question turn on the first discovery tick
A session whose watch row is created in this tick IS inspected for the question-turn milestone: if has_running_part && last_turn_tool === 'question' && last_notified_event !== 'question', notifyQuestionTurn fires in the same tick (inspectFreshSession), removing the +1 tick (~60s) latency. All other first-tick outcomes stay register-only: finished still requires a prior 'working'/'stopping' observation plus idle >= FINISH_CONFIRM_MINUTES (a fresh watch is born 'unknown', so it can never satisfy the guard on first sighting) and error never fires for fresh watches — do not weaken those guards or the 310-message bootstrap spam returns.

## Watcher finish confirmation window
OpencodeSessionWatcher does NOT notify "terminó" on the live working->stopped transition — opencode writes "thinking gaps" (step-finish -> step-start -> reasoning, none state.status='running') of 16-83s+ between tool calls, so an immediate notify was a false-positive factory (3 real sessions produced 37/5/39 parts after the notify). A stop promotes the watch to a 'stopping' candidate (no notify); the finish fires (notifyFinished) ONLY when last_seen_status is working/stopping AND effective last-activity (MAX(session.time_updated, MAX(part.time_created))) is idle >= FINISH_CONFIRM_MINUTES (3). A resume silently discards the candidate; fresh 'unknown'/'error'/'stopped' watches stay register-only. STABLE_RECHECK_MINUTES (5) applies only to confirmed 'stopped', 'stopping' candidates re-inspect every tick.

## recentParts() contract: role lives in message, noise types excluded
OpencodeSessionStore::recentParts(sessionId, limit=5, direction='last'|'first') returns significant parts in chronological ascending order (both directions) with role/tool/status/agent_name/sub_session_id/text/input/output. The role is NOT in part.data (verified null) — LEFT JOIN message on part.message_id and read message.data.role (null tolerated). Exclude noise types reasoning/step-start/step-finish/compaction by data.type. Long fields capped at LONG_FIELD_CAP (2000) so huge bash outputs can't blow memory. Never throws -> [] + Log::debug. OpencodeStoreFixture (tests/Support) has a message table + nullable part.message_id to test it.
