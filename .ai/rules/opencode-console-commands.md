# Opencode Console Commands

## Transcript parsing lives in OpencodeSessionParser, shared across monitors
Parsing of opencode conversation transcripts (lastAssistantText, conversationBlocks, hasQuestions, truncate) is centralized in App\Services\Opencode\OpencodeSessionParser — a final, stateless class injected into OpencodeMonitor::handle(). Do not re-implement these helpers in a new command; reuse the parser so external-session monitors share one implementation.

## opencode:monitor invokes OpencodeSessionWatcher to also watch external sessions
opencode:monitor calls OpencodeSessionWatcher::check() on every tick (before the workflow loop and also when no workflows are running), so it monitors ALL opencode sessions, not just bot workflows. Discovery: OpencodeSessionStore::activeSessions() lists every session straight from the opencode SQLite (read-only), applying the watermark to EFFECTIVE freshness (max of session.time_updated and the most recent part's time_created) because opencode does not bump session.time_updated on question parts; sessions with an opencode_workflows row are excluded; owner chat = resolveOwnerChatId() preferring a conversation inside TelegramSetting::allowed_user_ids over the latest one. Anti-spam: transitions tracked via opencode_session_watches.last_seen_status — a freshly discovered session is only registered (never notified on first sighting) EXCEPT a live 'question' turn, which is inspected (inspectFreshSession) and notified in the same discovery tick, and a failed Telegram notify leaves last_seen_status unchanged so the next tick retries. Question event = DB-first: only a session with a pending permission; a genuinely waiting session is handled earlier by the question-turn branch (DB signal last_turn_tool === 'question' on a live running part), and notifyFinished NEVER re-classifies a finish as a question from the assistant text — a rhetorical trailing question must not swallow the "La sesión ... terminó" message (bug real: final text '¿Procedemos con algo concreto...?' re-sent the already-answered question options and permanently suppressed the finish notification). Verified live: busy→idle transitions do fire.

## Boot summary excludes waiting sessions; question turn always fires (no dedup)
maybeSendBootSummary() lists ONLY working sessions in the "Sesiones activas desde el inicio del servidor:" summary; sessions with a live 'question' turn are excluded (bootSummarySessions skips last_turn_tool === 'question') and always get their own question-turn notification carrying the question text. There is NO boot-window dedup: do not suppress the question turn because the summary ran in the same tick, or the user loses the question content. Main discovery uses discoveryCutoff() (activeSessions($since - DISCOVERY_GRACE_MINUTES=5)) so a session that asked a question just before a watermark reset stays discoverable. A restart is detected authoritatively via the schedule_booted_at boot anchor (stamped by the CommandStarting listener for schedule:work in AppServiceProvider, so rapid restarts < 10 min re-emit the summary); the >10-min watermark heuristic is ONLY the fallback and applies solely when schedule_booted_at is null. When the anchor already exists and was adopted (session_watch_since == schedule_booted_at), resolveWatchSince() must NOT fall into the >10-min fallback (equality makes the anchor branch a no-op; falling into the elseif re-arms the boot marker and re-sends the summary ~10 min after the real boot). When no relevant session exists the boot STILL sends an immediate empty-boot message (formatBootSummaryEmpty, "Sistema DevWarden iniciado. No hay sesiones de opencode activas.") in the same tick — there is no retry window and no silent seal; the marker session_watch_boot_reported_at is persisted only after that notify() succeeds (a failed send is retried next tick).
